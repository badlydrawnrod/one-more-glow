# Game Input package and app adoption

## Objective

Agree and implement a browser-independent device input package, then adopt it in Asteroids and Very Angry Robots while preserving each game's accepted controls and transition behavior, subject to explicitly approved changes.

**Success criteria**

- The developer has explicitly accepted the relevant Game Input requirements and any changes to accepted app behavior before implementation of those requirements.
- Both apps consume `@one-more-glow/game-input` through its public entry point. The package has independent keyboard and per-connection gamepad state, no browser or app dependencies, and the accepted device-frame semantics.
- Both apps retain their accepted controls, screen and focus behavior, and Very Angry Robots retains ordered initials entry and touch controls. The accepted first-observation and focus-recovery differences are accounted for in the app specs and integrations.
- Package and app checks cover the applicable scenarios in the specs, and workspace checks and builds pass or remaining gaps are explicitly reported and handled under the closure rule.

Package-provided dead-zone profiles are deferred; consider a helper only if both consumers demonstrate the same semantics.

### Pre-planning scrutiny and decision gates

- **Layout compatibility:** Current game controllers use `KeyboardEvent.key` values; changing mappings directly to `code` can move letter controls on non-US layouts. Compare existing app bindings and accepted app specs with the proposed mapping. Present concrete alternatives and get the developer's decision before changing accepted controls. Code-based tracking does not require code-based action mappings.
- **Input sequencing:** A gameplay pressed set loses order and multiplicity. In particular, `A`, `A`, Backspace, Enter between updates must reach the app's initials editor in order, including submission; use an app-owned ordered path and keep gameplay actions suppressed. Check mixed keyboard, touch and gamepad editing against the app spec.
- **Lifecycle:** A button held when first observed is deliberately suppressed, and focus recovery deliberately differs from current behavior. Verify how each accepted app spec describes these cases and obtain separate approval for any changed accepted behavior before migration. An unseen disconnect and reconnect cannot be proven from a reused browser index: determine adapter reset boundaries during integration.
- **API precision:** The sketch does not settle all suppression semantics, including pending edges and snapshots taken at a transition. Review concrete event sequences and record decisions before implementing affected behavior. Duplicate connection tokens must reject a read without changing *any* tracking state, including pending keyboard edges.
- These are known questions to resolve during the planned review and integration, as agreed with the developer. Their answers may alter the design or sequence; update this plan and the owning specs rather than silently assuming them.
